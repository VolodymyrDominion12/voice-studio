# Концепція фронтенду Voice Studio

**Статус:** концепція **реалізована** — фази F0–F3 зроблено, з F4 зроблено
найважливіше: витяг тексту з PDF / DOCX / EPUB / HTML (див. розд. 17),
**аудіокнига** (M4B із розділами, ID3-теги, zip по розділах) і вибір формату
результату. Пройдено повний цикл «завантажити файл → підготувати текст →
озвучити → скачати MP3/M4B» — і для `.md`, і для PDF.
`pytest` — 219 passed, `ruff` — 0 зауважень.
Не зроблено з F4: зразки голосів (усі голоси читають спільну еталонну фразу)
і клонування голосу.
**Стек:** зафіксовано в [ADR-008](DECISIONS.md) — Jinja2 + htmx + Alpine.js,
серверний рендеринг, без кроку збірки. Цей документ не переглядає стек, він
описує **що саме** будується на ньому.
**Візуальний макет:** [`docs/frontend-mockup.html`](frontend-mockup.html) —
статичний клікабельний макет усіх екранів (дані вигадані, до API не підключений).

## 1. Що означає «всі операції з інтерфейсу»

Критерій, за яким написано цей документ:

> Жодна дія, потрібна для отримання готового аудіофайлу, не вимагає `curl`,
> Swagger `/docs`, SQL-клієнта або редагування файлів на диску.

Перелік нижче виведено не з фантазії, а з коду (`app/api/`, `app/services/`,
`app/worker/`) і документації ([ARCHITECTURE](ARCHITECTURE.md) розд. 2–5,
[PLAN](PLAN.md) етапи 1–2). Колонка «API» показує стан **на сьогодні**:

* ✅ — ендпоінт існує й працює;
* 🟡 — ендпоінт існує, але з обмеженнями (описані в розд. 16);
* ❌ — ендпоінта немає, його треба додати (розд. 16).

третини роботи — у фронтенді й одна третина — у бекенді** (розд. 16).

## 2. Передумови (виконано у фазі F0)

> **Стан: закрито.** Обидва блокери виправлено під час реалізації F0, рефакторинг
> зроблено. Розділ лишається як запис про те, чому F0 стояла першою, і як
> перевірявся кожен крок.

Перший екран неможливо було навіть відкрити, доки не закрито два блокери з
[README §11](../README.md#11-відомі-проблеми-й-обмеження). Обидва перевірено
заново під час написання цього документа:

| Що | Було | Наслідок для UI | Як закрито |
|---|---|---|---|
| **Блокер 1** — `InvalidRequestError: relationship("list['Block']")` | `/api/v1/documents` і `/api/v1/jobs` → **500**; вставка `Document` падала тим самим винятком | Список документів, завантаження, черга — усе порожнє. Показувати нічого | Прибрано `from __future__ import annotations` з `app/models.py` (+ попередження в докстрінгу, щоб не повернули) |
| **Блокер 2** — наївний `datetime` не пишеться в SQLite | Падало на першому ж `commit()` після фіксу #1 | UI показував би «Помилку сервера» на кожному збереженні | Поля часу анотовані `NaiveDatetime` (**з pydantic** — у SQLModel 0.0.47 його немає на верхньому рівні); «зараз» створює єдина `utc_now()` |

Що при цьому **вже працювало** (перевірено: `200`): `/api/v1/health`,
`/api/v1/engines`, `/api/v1/emotions`, і `POST /api/v1/preview` — за умови
живого TTS-шлюзу.

Тому в концепції прийнято таке правило:

> **UI не перевіряється на «порожньому» бекенді.** Фаза F0 цього плану —
> виправлення блокерів і винесення логіки з `api/documents.py` у сервіс. Макет
> (`frontend-mockup.html`) можна показувати й зараз, бо він не ходить у мережу.

Додаткова передумова — **рефакторинг перед першим шаблоном**: у
`app/api/documents.py` логіка завантаження (sha256, збереження файлу, витяг,
нормалізація) жила прямо в обробнику. UI-роутер має викликати ту саму логіку,
а не дублювати її HTTP-викликом у самих себе. Отже:

```
app/services/library/         ← нове: керування документами як сервіс (зроблено)
    errors.py      LibraryError, UnsupportedFormatError, UploadTooLargeError…
    documents.py   create_from_upload(), get_document_with_blocks(), renormalize()
    blocks.py      block_effective_text(), count_speakable(), update_block(s)
app/api/documents.py           ← стає тонким: розбір запиту + серіалізація
app/ui/                        ← нове: HTML-поверхня (розд. 4)
    router.py       маршрути: /, /documents/{id}, /settings, /ui/*
    templating.py   налаштування Jinja2 (фільтри, глобальні функції)
    presentation.py підписи, бейджі, форматування — уся «косметика» UI
```

Фаза F0 обійшлася одним `router.py`: маршрутів мало. Розділення на
`documents.py` / `editor.py` / `jobs.py` / `voices.py` / `system.py` варто
зробити у F1–F2, коли їх стане суттєво більше (і зʼявляться htmx-фрагменти).

Один код — дві поверхні: JSON для `/api/v1`, HTML для `/ui`. Це єдиний спосіб
не розʼїхатися двом реалізаціям однієї дії.

## 3. Принципи дизайну

1. **Слухай перед тим, як озвучувати все.** Головний страх користувача —
   витратити 20 хвилин CPU на неправильний голос. Тому прев'ю блоку доступне
   з першого екрана редактора й коштує секунди (ARCHITECTURE §4 прямо називає
   це критичним для UX).
2. **Кожна довга дія — завдання, а не «зависання».** Озвучення 10-хвилинного
   розділу на CPU — це одиниці хвилин або й ~20 (ARCHITECTURE §8). Отже:
   прогрес, ETA, можливість закрити вкладку, повернутися, скасувати.
3. **Сервер — єдине джерело правди.** Жоден стан не живе тільки в браузері.
   F5 ніколи не втрачає роботу. Alpine тримає лише те, що нешкідливо втратити:
   відкриті панелі, фокус, незбережений чернетковий рядок.
4. **Текст — головний об'єкт, контроли — другорядні.** Це щільний редактор
   книги, а не форма з трьох полів. Контроли не мають «зʼїдати» ширину тексту.
5. **Чесність про межі.** Замість магії — видимі факти: що рушій уміє нативно
   (`capabilities`), скільки символів долетить до рушія, що прев'ю **не**
   відтворює паузи між сегментами, скільки сегментів буде синтезовано.
6. **Ніколи не блокувати інтерфейс.** Ніяких модальних «зачекайте» на весь
   екран: частковий результат доступний одразу — сегменти пишуться на диск
   в міру готовності (ідемпотентність, ADR-007), отже й прослуховувати їх
   можна в міру готовності.
7. **Нічого не робити мовчки.** Кожна дія має видимий наслідок: чип «Збережено»,
   тост, оновлений рядок, змінений лічильник. Користувач не має питати «а
   воно збереглося?».

## 4. Карта екранів і маршрутів

```
  /                       Робоча стола: завантаження · документи · активна черга
   │
   ├── /documents/{id}     Редактор: блоки · емоції · прев'ю · «Озвучити все»
   │
   ├── /jobs               Черга: усі завдання · прогрес · скасування
   │    └── /jobs/{id}     Завдання: сегменти · плеєр · завантаження · помилки
   │
   ├── /voices             Рушії та голоси · capabilities · прослухати голос
   │
   └── /settings           Система: health · емоції · діагностика · пресети
```

Два типи маршрутів, і їх важливо не змішувати:

| Тип | Префікс | Віддає | Хто викликає |
|---|---|---|---|
| **Сторінки** | `/`, `/documents/{id}`, `/jobs`, `/voices`, `/settings` | повний HTML | браузер (навігація, F5) |
| **Фрагменти** | `/ui/...` | HTML-шматок (без `<html>`) | htmx |
| **API** | `/api/v1/...` | JSON / WAV / MP3 | htmx лише для SSE та плеєра; зовнішні клієнти |

Фрагменти — окремий простір імен, а не `/api/v1` з `Accept: text/html`:
інакше кожен JSON-клієнт тягне за собою знання про шаблони.

### Таблиця фрагментів (`/ui`)

| Метод | Шлях | Повертає | Викликається з |
|---|---|---|---|
| `POST` | `/ui/documents` | рядок документа + тост | dropzone на `/` |

## 5. Екран 1 — Робоча стола `/`

Призначення: «що я маю і що зараз робиться». Один екран відповідає на три
питання: куди кинути файл, що вже завантажено, чи живий синтез.

```
┌────────────────────────────────────────────────────────────────────────────┐
│ Voice Studio      Робоча стола · Голоси · Система      ● шлюз живий  v0.1.0 │
├────────────────────────────────────────────────────────────────────────────┤
│                                                                            │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │   Перетягніть файл сюди  або  [ Обрати файл ]                        │  │
│  │   .txt · .md — до 50 МБ. PDF/DOCX/EPUB: етап 2.                      │  │
│  │   ▓▓▓▓▓▓▓▓▓▓░░░░░░░░  завантаження · витяг блоків · нормалізація     │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│  Документи                                          [ пошук ] [ усі ▾ ]     │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │ розділ-1.md        142 блоки · 3 змінені · готовий      [ Відкрити ] │  │
│  │ оповідання.txt      38 блоків · 0 змінених · готовий    [ Відкрити ] │  │
│  │ scan-book.pdf       —        помилка: це скан, потрібен OCR          │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                                                            │
│  Зараз виконується                                                    (2/2)│
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │ #7  розділ-1.md → tetiana-high                                    42% │  │
│  │ ▓▓▓▓▓▓▓▓░░░░░░░░░░░░  сегмент 76/180 · залишилось ~6 хв  [Скасувати] │  │
│  │ #8  оповідання.txt → mykyta-high              у черзі (позиція 1)     │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────────────┘
```

**Елементи та їхні джерела**

| Елемент | Джерело |
|---|---|
| Чип «шлюз живий» | `GET /api/v1/health` + пропозиція пробника шлюзу (16.9) |
| Dropzone | `POST /ui/documents` → `POST /api/v1/documents` |
| Ліміт «до 50 МБ» | `max_upload_mb` (зараз не застосовується — 16.7) |
| Дозволені формати | `allowed_extensions`; нереалізований екстрактор → 422 з підказкою |
| Рядок документа | `GET /api/v1/documents` + підрахунок змінених блоків |
| Стрічка «Зараз виконується» | `GET /ui/queue` (5 с) + SSE, якщо користувач на `/jobs` |

**Стани**

* *Порожньо:* «Ще немає жодного документа. Перетягніть `.txt` або `.md` — і
  через кілька секунд побачите текст, розбитий на блоки.» (Не «No data».)
* *Завантаження:* три підкроки в одному прогрес-барі (передача → витяг →
  нормалізація), бо саме третій крок найдовший і його відсутність у прогресі
  виглядає як зависання.
* *Дублікат:* бекенд повертає **існуючий** документ за `sha256`, а не створює
  новий. UI мусить це озвучити: «Цей файл уже завантажено — відкриваю наявну
  копію», інакше користувач вирішить, що завантаження не спрацювало.
* *Формат не підтримується (415):* тост із переліком дозволених розширень.
* *Екстрактор не реалізовано (422):* «PDF ще не читається — це етап 2 плану.
  Спробуйте `.txt` або `.md`.» Посилання на `docs/PLAN.md`.
* *Скан-PDF (евристика ARCHITECTURE §2.1, <100 символів/стор.):* окреме
  повідомлення «схоже на скан», а не загальна помилка.

## 6. Екран 2 — Редактор `/documents/{id}`

**Це головний екран застосунку.** 80% часу користувач проводить тут. Усе інше —
обслуговування.

### 6.1 Каркас

```
┌────────────────────────────────────────────────────────────────────────────┐
│ ← оповідання.txt    142 блоки · 3 змінені · ~28 хв аудіо                   │

### 6.2 Анатомія рядка блоку

| Зона | Вміст | Чому так |
|---|---|---|
| Ліва шпальта | `ordinal`, бейдж типу (`H1…H6`, `¶`, `❝`, `•`, `</>`, `▦`, `*`), чекбокс `speak` | Тип видно одразу; вимкнення озвучення — одна дія, бо для коду/таблиць це типова поведінка |
| Тіло | текст у режимі перегляду, `textarea` у режимі правки | Текст домінує за шириною |
| Підрядок контролів | емоція + інтенсивність + прочитана просодія + ▶ + стан збереження | Усе, що стосується блоку, — під блоком, а не в окремій панелі |
| Розкриття «різниця» | `text_raw` vs `text_normalized` vs `text_edited` | Вимога PLAN етапу 2: показ різниці, а не лише трьох текстів |

**Прочитана просодія** («темп 0.98×, пауза після 460 мс») — не прикраса.
Дані для неї вже є: `GET /api/v1/emotions` віддає таблицю профілів, а формула
масштабування за `intensity` — це `get_prosody()` з
`app/services/expression/profiles.py` (лінійна інтерполяція від `neutral`).
UI показує **наслідок вибору** ще до синтезу — це прямо адресує ADR-004
(«керована просодія, а не гра моделі») без магії.

### 6.3 Три тексти й правило одного власника

Три поля (`text_raw`, `text_normalized`, `text_edited`) — джерело плутанини,
якщо не зафіксувати правило:

| Поле | Хто пише | Хто читає |
|---|---|---|
| `text_raw` | екстрактор, один раз | режим «Вихідний», різниця |
| `text_normalized` | нормалізатор (повторно) | режим «Нормалізований», різниця |
| `text_edited` | **користувач** | синтез; якщо порожнє — синтез бере нормалізований |

Правила, які UI зобов'язаний виконувати:

1. **Синтез завжди бере `text_edited or text_normalized or text_raw`** — рівно
   як у `worker/queue.py`. UI не вигадує власного пріоритету.
2. Кнопка «Повернути до нормалізованого» = `PATCH {text_edited: ""}`, а не
   копіювання тексту в поле. Інакше блок назавжди стає «зміненим».
3. «Перенормалізувати» **не чіпає** `text_edited`: повторна нормалізація — це
   про `text_normalized`. Після неї в редакторі може виникнути конфлікт
   (користувач правив те, що змінилося під ним) → показувати чип
   «нормалізацію оновлено, ваш текст збережено» на змінених блоках.

### 6.4 Збереження

Обрано **автозбереження з дебаунсом 1.5 с + явний `Ctrl+S`**, а не «кнопка
Зберегти на кожен блок»:

* `PATCH` дешевий (один рядок у SQLite), тож дебаунс не створює навантаження;
* користувач не втрачає роботу при закритті вкладки — а це найчастіша втрата
  в текстових редакторах;
* видимий стан: `● Незбережено` → `◌ Зберігаю…` → `✓ Збережено 14:02`.

Конфліктність виключена: один користувач, один документ (багатокористувацький
режим — поза межами MVP, ARCHITECTURE §9).

### 6.5 Прев'ю блоку — і його чесні межі

Кнопка ▶ робить `POST /ui/blocks/{bid}/preview` → `POST /api/v1/preview` і
вставляє `<audio controls autoplay>` під блоком (без перезавантаження сторінки).

Що UI **зобов'язаний** сказати користувачеві, бо інакше прев'ю обманює:

| Межа | Чому | Текст у UI |
|---|---|---|
| Обрізання за `caps.max_chars` (500 у Speaches) | `preview.py` робить `text[:caps.max_chars]` **мовчки** | «Показано перші 500 символів із 780» — і попередження ще до натискання |
| Паузи не застосовуються | Пауза вставляється при склейці (`assemble.py`), а прев'ю — один сегмент | «Пауза після блоку (460 мс) додається під час збірки» |
| Перший виклик повільний | Завантаження моделі в шлюзі | Скелетон + «перший синтез довший: модель завантажується» |
| `engine_id` у запиті ігнорується | `preview.py` жорстко бере `openai_compat` | Селектор рушія **вимкнений** у режимі прев'ю, доки 16.4 не закрито |
| Ефект емоції на голосі без `emotions: true` | Це просодія, а не акторська гра | Підказка за ADR-004, один раз на документ (не на кожен блок) |

### 6.6 Масові дії

Виділення кількох блоків (чекбокси зліва + `Shift+клік` по діапазону) показує
панель: **емоція ▾** · **інтенсивність ▓** · **озвучувати/не озвучувати** ·
**слухати вибрані послідовно** · **зняти виділення**.

Технічно потрібен `PATCH` для багатьох блоків (16.5): 142 блоки × окремий
`PATCH` — це 142 запити й 142 перерендери, що на очах перетворюється на
«задумливий» інтерфейс.

### 6.7 Довгі документи

Книга — це 1000+ блоків. Тому:

* блоки рендеряться **сторінками по 50** (`GET /ui/documents/{id}/blocks?offset=`),
  решта — за кнопкою «Показати ще» (або `hx-trigger="revealed"` на сентинелі);
* пошук і фільтри — **на сервері**, не в DOM;
* «Озвучити все» рахує сегменти **на сервері** (той самий `split_sentences` з
  `max_chars` рушія), бо клієнтська оцінка розійдеться з реальністю;
* лічильник «~28 хв аудіо» — оцінка за символами (порядок ~14 символів/с для
  Piper medium). Це **оцінка, а не вимір**: реальний real-time factor для цієї
  машини має дати `scripts/benchmark.py` (PLAN, етап 1). UI зобов'язаний писати
  «≈» і не подавати число як факт;

### 6.8 Гарячі клавіші

| Клавіша | Дія |
|---|---|
| `J` / `K` | фокус на наступний / попередній блок |
| `Space` | прослухати блок у фокусі |
| `E` | відкрити вибір емоції |
| `1…8` | емоція за порядком у списку (коли відкритий вибір) |
| `S` | перемкнути «озвучувати» |
| `Ctrl+S` | зберегти всі незбережені блоки |
| `Ctrl+Enter` | прослухати блок у фокусі |
| `Ctrl+Shift+Enter` | «Озвучити все» (з підтвердженням) |
| `Esc` | закрити панель / зняти виділення |

Клавіатурний шлях має покривати **всю розмітку емоцій**: 142 блоки мишкою —
це 142 рази «наведи-клацни-обери», що фізично втомлює.

## 11. Модель стану

Три шари, і кожен факт має рівно одного власника:

| Шар | Живе в | Приклади | Втрата при F5 |
|---|---|---|---|
| **Серверний** (істина) | SQLite | текст блоків, емоції, статуси, файли | неможлива |
| **URL** | адреса | `?mode=normalized&offset=100&filter=edited&emotion=warm` | відновлюється |
| **Локальний** | Alpine | відкриті панелі, фокус, незбережений рядок, виділення | припустима |

Наслідки:

* фільтри й режим перегляду **живуть в URL** — посилання «ось блоки, які я
  позначив теплими» можна надіслати собі ж;
* ніщо не дублюється: емоція не зберігається в Alpine, бо вона на сервері;
* Alpine використовується точково (`x-data` на рядок блоку й на панель
  виділення), а не як «застосунок у застосунку» — інакше ADR-008 втрачає сенс.

## 12. SSE: життєвий цикл і деградація

Схема підключення на `/jobs/{id}` та в стрічці черги:

```
1. GET /api/v1/jobs/{id}        ← знімок (сьогодні відсутній: 16.1)
2. EventSource /api/v1/jobs/{id}/events
3. progress → смуга, лічильник, ETA (ковзне середнє за останні 5 подій)
4. segment  → рядок сегмента стає «готовий» + плеєр
5. finished → кнопка завантаження, тост, оновлення списку документів
6. error/cancelled → чип, текст помилки, «Повторити»
```

Обов'язкові деталі, які легко пропустити:

* **Знімок обов'язковий.** SSE віддає лише **майбутні** події (у
  `jobs.py` підписка створюється в момент запиту) і не має ні
  `Last-Event-ID`, ні події-знімка. Отже без попереднього `GET` сторінка після
  F5 показує 0% і «нічого не відбувається», доки не прийде наступний сегмент.
* **Keepalive.** Сервер шле `: keepalive` кожні 30 с — клієнт мусить його
  ігнорувати, а не вважати подією (інакше тост на кожні 30 с).
* **Реконект.** `EventSource` відновлюється сам, але після завершення
  завдання стрім закривається штатно — не показувати «зʼєднання втрачено».
* **Вкладка у фоні.** Браузер може призупинити стрім; на `visibilitychange →
  visible` робити `GET` знімка, а не сподіватися на «доганяючі» події.
* **Деградація.** Якщо SSE не піднявся (проксі, дивний браузер) — перейти на
  опитування `GET /ui/jobs/{id}/card` кожні 3 с. Інтерфейс не має лишатися без
  прогресу за жодних обставин.
* **Кілька завдань.** Одна `EventSource` на **видиму** картку. Для стрічки на
  робочій столі — опитування `/ui/queue` раз на 5 с: тримати N зʼєднань заради
  смужки прогресу марнотратно.

## 14. Доступність, клавіатура, локалізація

* Мова інтерфейсу — **українська**, усі рядки в шаблонах (не в JS). Числа,
  дати й розміри — через один хелпер форматування (`4:12`, `18.4 МБ`, `~6 хв`).
* `aria-live="polite"` на чипі статусу завдання та на тостах; `role="progressbar"`
  з `aria-valuenow` на кожній смузі.
* Прогрес озвучення **не** озвучується скрін-рідером на кожен сегмент (180
  подій) — лише на зміну статусу і кожні 10% (інакше це катування).
* Кнопка ▶ має текстову назву («Прослухати блок 12»), а не лише іконку.
* `prefers-reduced-motion` вимикає анімацію смуг.
* Контраст ≥ 4.5:1; емоції розрізняються не лише кольором, а й словом
  («warm», «сум») — колір як єдиний носій інформації неприпустимий.
* Аудіо: нативний `<audio controls>`; для сегментів — мініплеєр із видимою
  тривалістю. Одночасне відтворення заборонене (новий ▶ зупиняє попередній).

## 15. Дизайн-токени і CSS

ADR-008: Tailwind через CDN на час розробки, далі зібраний CSS. Щоб «далі» не
перетворилося на переписування, токени фіксуються одразу:

| Токен | Значення |
|---|---|
| Статусні кольори | `queued` — сірий, `running` — синій, `done` — зелений, `failed` — червоний, `cancelled` — бурштиновий, `stalled` — фіолетовий |
| Емоції | 8 відтінків від холодного (sad/serious) до теплого (joyful/excited) + **текстова назва завжди поруч** |
| Типографіка блоків | `H1` 1.6rem/700, `H2` 1.35rem/600, `¶` 1rem/400, `❝` курсив + ліва лінія, `</>` моно, `▦` моно + сітка |
| Щільність | базовий рядок блоку ~64 px; компактний режим ~48 px (перемикач) |
| Ширина тексту | `max-width: 72ch` — довгі рядки вбивають читабельність при правці |
| Радіуси/тіні | мінімальні: межа 1 px замість тіні, де можливо |

Адаптивність: до планшета (768 px) — робоча; телефон — лише перегляд черги й
прослуховування, бо правка 1000 блоків на телефоні не має сенсу (і це чесніше,
ніж вдавати повну підтримку).

### 16.2 Знахідка: «відновлення після перезапуску» не працює на рівні завдання

ADR-007 обіцяє, що після падіння процесу синтез продовжується з місця зупинки.
**Ідемпотентність сегментів** справді є (`worker/queue.py`: якщо WAV існує —
синтез пропускається), але **ніщо не перезапускає саме завдання**:

* черга — це `asyncio.Queue`, яка живе лише в пам'яті процесу
  (`_get_queue()`, `worker_loop()`);
* у `lifespan()` (`app/main.py`) викликається `reset_queue()` — тобто черга не
  просто порожня, а явно скинута;
* завдання, що лишилися в `queued`/`running`, ніколи не буде поставлено в
  чергу знову, і ендпоінта для цього немає.

**Стан: закрито** — формати тепер створюються на етапі збірки
(`options.formats` + `chapter_split`), і параметр `format` віддає один із
реально створених файлів. Незамовлений формат — `404` зі списком наявних
(раніше був `409` без пояснення).

**Наслідок для UI:** стан `⚠ перервано` (розд. 7.1) треба не лише намалювати,
а й мати чим його закрити. **Мінімальне виправлення:** у `lifespan()` після
`create_db_and_tables()` знайти завдання зі статусом `queued`/`running`,
перевести `running` → `queued` і викликати `enqueue_job()` для кожного. Це
~10 рядків і воно повертає обіцянку ADR-007.

### ✅ 16.3 (закрито) — `?format=` у завантаженні не працює

`app/api/jobs.py::download_result` бере `format` лише для `media_types`, а
файл завжди віддає з `job.output_path`. Тобто `?format=wav` на MP3-результаті
поверне **MP3-байти з `Content-Type: audio/wav`**. UI не має права пропонувати
вибір формату, доки це не виправлено (або не зроблено конвертацію на льоту).

### 16.4 Знахідка: прев'ю ігнорує `engine_id` і мовчки обрізає текст

`app/api/preview.py`: `engine = get_openai_compat_engine()` — жорстко; поле
`engine_id` у `PreviewRequest` не використовується. Плюс
`text[: caps.max_chars]` обрізає без жодного сигналу клієнту. Для UI це означає
вимкнений селектор рушія в прев'ю і власний підрахунок символів (розд. 6.5).

### 16.5 Масові дії без bulk-ендпоінта

`PATCH /documents/{id}/blocks/{bid}` — по одному блоку. Для розмітки книги це
N запитів. Потрібен варіант зі списком `[{block_id, emotion, intensity}]`, який
у межах однієї транзакції оновлює все й повертає оновлені блоки.

### 16.6 Таблиця `voices` і `presets` не використовуються

Моделі `Voice` і `Preset` оголошені в `app/models.py`, але: голоси приходять із
`_ENGINE_CATALOGUE` (`app/api/engines.py`) у пам'яті, `sample_path` порожній,
пресети не мають жодного ендпоінта. Для UI це означає: «прослухати голос»
можна лише через прев'ю еталонної фрази, а пресети треба або доробити, або
свідомо винести з MVP (і тоді прибрати екран пресетів із концепції).

### 16.7 `max_upload_mb` не застосовується

У `config.py` ліміт є, у `upload_document` він не перевіряється. UI має
перевіряти розмір **на клієнті** (щоб не ганяти 78 МБ даремно), але це не
заміна серверній перевірці.

### 16.8 Дрібніші, але помітні в UI

| # | Що | Наслідок в UI |
|---|---|---|
| a | Імʼя файлу використовується як шлях без очищення (`data/uploads/<filename>`) | стає суттєвим, щойно завантаження стає кнопкою в браузері; рекомендується `uuid`-імʼя + оригінальна назва в БД |
| b | `JobRead` не містить назви документа | список завдань вимагає N+1 запитів; у HTML-роутері знімається JOIN-ом, але JSON-клієнтам це шкодить |
| c | Повторний запуск завдання додає сегменти **дублем** | `UNIQUE(job_id, block_id, ordinal)` з ARCHITECTURE §3 у `Segment` не оголошено, тож рядки накопичуються; UI має дедуплікувати, а краще — зробити upsert |
| d | Порожній документ/усі блоки `speak=false` | завдання створюється й падає з «Немає блоків для синтезу»; краще 422 до створення |
| e | `POST /jobs` не перевіряє існування документа | те саме: помилка на етапі завдання замість етапу запиту |
| f | Немає ключа ідемпотентності на створення завдання | подвійний клік «Озвучити все» створить два завдання → UI має вимикати кнопку до відповіді |

* ✅ Бекенд: `GET /jobs/{id}`, `/jobs/{id}/segments`, аудіо сегмента,
  `/jobs/{id}/retry`, перезапуск незавершених завдань при старті (16.2),
  дедуплікація рядків сегментів (16.8c), валідація створення завдання (16.8d),
  чесний `?format=` (16.3).

**Критерій виконано:** повний цикл «завантажити → озвучити → скачати MP3»
пройдено через інтерфейс; перезапуск процесу повертає завдання в чергу.

### ✅ F3 — масштаб і зручність — зроблено

* ✅ Пагінація блоків (200 на сторінку, htmx довантажує в кінець списку),
  серверні фільтри (пошук, «лише змінені», за емоцією).
* ✅ Масові дії: емоція, озвучувати/не озвучувати для виділених (bulk-PATCH
  однією транзакцією).
* ✅ Сегментний плеєр (`/jobs/{id}/segments` + аудіо кожного сегмента).
* ✅ Гарячі клавіші (`J`/`K`, `Space`, `E`, `S`, `Ctrl+S`, `Esc`).
* ✅ `/voices` із прослуховуванням голосів на спільній еталонній фразі.
* ✅ Пресети: CRUD-API + створення з редактора + застосування емоції до всіх
  блоків (питання 1 із розд. 20 закрито рішенням «доробити»).

**Критерій виконано частково:** на книзі 1000+ блоків не прогнано (механізми
є, вимірювання немає), жодна дія не вимагає чекати завершення всього синтезу.

### 🟡 F4 — зроблено частково

* ✅ **PDF/DOCX/EPUB/HTML.** `.pdf` — PyMuPDF із визначенням заголовків за
  розміром шрифту, зшиванням переносів і **евристикою скана**; решта —
  markitdown (метадані відкидаються, щоб диктор не читав «Title, Language»).
  Витяг перевірено на справжніх файлах усіх форматів (23 тести).
* ✅ **Просодія справді застосовується** (понад план F4): пауза після кожного
  сегмента береться з його профілю, на межі абзацу множиться на 1.5, а
  `energy_db` коригує гучність сегмента ДО глобальної нормалізації — тож
  динаміка між сегментами зберігається. Доти емоція впливала лише на темп.
* ✅ **M4B із розділами, ID3-теги, zip по розділах.** Нативний `ffmpeg`
  виявився не потрібен: M4B/AAC кодує PyAV (колесо зі вбудованими
  бібліотеками FFmpeg, ADR-013), теги пише `mutagen`. Розділи беруться з
  заголовків документа, а їхні межі — з таймлайну сегментів.
* ✅ **Вибір формату вивантаження** — MP3 / M4B / WAV і «zip по розділах»
  вибираються чекбоксами при створенні завдання; `?format=` віддає саме той

* ❌ **Зразки голосів** — замінені спільною еталонною фразою; окремі семпли
  (`voices.sample_path`) не заповнюються.
* ❌ **Клонування голосу** (ZONOS2) — залежить від етапу 3.1.
* ❌ **LLM-розмітка емоцій** — UI як «перегляд і правка пропозиції», ніколи як

## 18. Критерії приймання

### 18.1 Чеклист «всі операції з UI»

Фронтенд вважається готовим до заяви «всі операції доступні», коли **кожен**
пункт розд. 1 виконується в браузері, а колонка «API» для нього — ✅ або
свідомо виключена з MVP із записом у README. Чеклист ведеться як
`docs/FRONTEND-CHECKLIST.md` і оновлюється разом із кодом (той самий підхід,
що й у README §0 — чесна карта стану).

### 18.2 Наскрізний ручний сценарій

1. Відкрити `/` → завантажити `.md` на 10 абзаців.
2. Побачити 10 блоків, перевірити різницю «вихідний/нормалізований».
3. Змінити текст абзацу 3 → дочекатися чипа «Збережено».
4. Поставити абзацу 3 емоцію `warm`, інтенсивність 0.6 → побачити «темп 0.98×,
   пауза 460 мс».
5. Натиснути ▶ → почути абзац 3.
6. Позначити блок коду як «не озвучувати».
7. Обрати голос `mykyta-high` → ▶ на абзаці 1 → почути інший голос.
8. «Озвучити все» → побачити смугу, прогрес, ETA, поточний блок.
9. Піти на `/jobs/{id}` → прослухати вже готовий сегмент, поки решта пишеться.
10. Скасувати → побачити «Скасовано, часткові сегменти збережено».
11. Запустити знову → переконатися, що готові сегменти не синтезуються вдруге.
12. Дочекатися завершення → завантажити MP3 → відтворити файл.
13. Вимкнути Docker-контейнер шлюзу → спробувати прев'ю → побачити зрозумілу
    помилку з підказкою, а не 500.

### 18.3 Автоматичні перевірки

## 19. Що свідомо не входить

| Не робимо | Чому |
|---|---|
| SPA (React/Vue) | ADR-008: зайвий тулчейн для документо-центричного UI |
| Реєстрація, ролі, мультикористувацькість | ARCHITECTURE §9: локальний одноосібний застосунок |
| Мобільний першочерговий дизайн | правка книги на телефоні — не сценарій; лишається перегляд і прослуховування |
| Drag-and-drop зміна порядку блоків | порядок = структура документа; змінювати його означає розійтися з вихідним текстом |
| Візуальний еквалайзер просодії | ADR-004: керована просодія в консервативних межах, не «крутилки» |
| Клонування голосу в UI | ADR-010/ARCHITECTURE §9: поза MVP; у ZONOS2 — лише якщо етап 3.1 дасть «так» |
| OCR-інтерфейс | не в MVP (ARCHITECTURE §9) |
| Dark mode як окрема тема | бажано, але не входить у критерій «всі операції»; токени (розд. 15) його не блокують |

## 20. Рішення щодо відкритих питань

Питання, які стояли перед реалізацією, і як їх закрито:

1. **Пресети — доробляти чи викреслити?** → **Дороблено.** CRUD-API
   (`/api/v1/presets`) + створення з редактора + застосування емоції до всіх
   озвучуваних блоків. Таблиця вже існувала, а «викреслити» вимагало б
   прибирати її з моделі — доробити виявилось дешевше.
2. **Автозбереження vs явне збереження?** → **Автозбереження** з дебаунсом
   1.5 с + `Ctrl+S` для негайного збереження всього. Чип стану показує
   «Незбережено → Зберігаю → Збережено HH:MM», а `beforeunload` попереджає,
   якщо щось лишилось незбереженим.
3. **Один екран чи два для черги?** → **Два** (`/jobs` і `/jobs/{id}`):
   на сторінці завдання живе SSE-підписка й сегментний плеєр, у списку —
   лише прогрес. Одна підписка на видиме завдання замість N.
4. **Порядок фаз?** → **F0 першою**, як і планувалось: блокери закрито до
   першого шаблону, тож жодного техборгу на фікстурах не зʼявилося.
5. **Чи показувати оцінку тривалості й ETA?** → **Показуємо, але з «≈»**:
   і оцінка за символами, і ETA рахуються з попередженням, що точність
   приблизна (ARCHITECTURE §8).

**Нові питання, які варто вирішити перед F4:**

* **Ключ ідемпотентності на створення завдання.** Зараз подвійний клік
  захищений лише вимкненням кнопки в UI; у JSON-API захисту немає.
* **`GET /api/v1/health/tts`** — щоб «шлюз живий» не вимагав синтезу фрази.
* **Компактний режим рядка блоку** (задумано в розд. 15, не реалізовано).
* **Dark mode** — токени готові, перемикача немає (у макеті він був).
