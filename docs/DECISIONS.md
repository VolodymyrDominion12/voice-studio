# Журнал архітектурних рішень (ADR)

Формат: кожне рішення — контекст, рішення, наслідки, відкинуті альтернативи.
Рішення можна переглядати; застарілі позначаються `ЗАМІНЕНО`, а не видаляються.

---

## ADR-001. Шар абстракції над рушієм TTS

**Статус:** прийнято

**Контекст.** Ринок TTS-моделей змінюється кожні кілька місяців: XTTS-v2 був
стандартом у 2023-му, у 2025-му з'явилися Chatterbox, IndexTTS-2, Higgs Audio v2.
Застосунок, який «вшиває» одну модель, доведеться переписувати. Крім того,
жодна вільна модель не покриває одночасно українську мову і керування емоціями
(див. ADR-003 і ADR-004), тому в проєкті **за визначенням** буде кілька рушіїв.

**Рішення.** Уся робота з моделями ховається за інтерфейсом `TTSEngine`:

```python
class TTSEngine(Protocol):
    id: str
    def voices(self) -> list[Voice]: ...
    def capabilities(self) -> EngineCapabilities: ...   # які емоції/теги підтримує
    def synthesize(self, req: SynthRequest) -> AudioChunk: ...
    def supports_streaming(self) -> bool: ...
```

Конкретні рушії — окремі адаптери в `app/services/tts/`:
`piper.py`, `ukrainian_tts.py`, `openai_compat.py` (будь-який
`/v1/audio/speech`-сервер: Speaches, Kokoro-FastAPI, хмарний API),
`chatterbox.py`, `xtts.py`.

**Наслідки.**
- `capabilities()` дозволяє застосунку **деградувати коректно**: якщо рушій не
  вміє емоцію, шар виразу (ADR-004) бере її на себе, а не мовчки ігнорує.
- Зміна рушія = зміна рядка в конфізі, а не рефакторинг.
- Ціна: трохи зайвої абстракції; для MVP з одним рушієм виглядає надмірно, але
  окупається на етапі 3.

**Відкинуто.** Пряме використання `piper-tts` у коді застосунку — швидше
написати, неможливо розвивати.

## ADR-002. Python 3.11, закріплений через `uv`

**Статус:** прийнято

**Контекст.** Системний Python — 3.13.9. Але:
- `openedai-speech`: «tested with python 3.9-3.11, piper does not install on
  python 3.12 yet»;
- `kokoro` (PyPI) вимагає `>=3.10,<3.13`;
- оригінальний `TTS` (Coqui) вимагає `<3.12`;
- частина коліс `torch`/`espnet` відстає від найновіших версій.

**Рішення.** Проєкт використовує Python 3.11, встановлений і закріплений через
`uv` (`uv python install 3.11`, `requires-python = "==3.11.*"` у
`pyproject.toml`). Системний Python не чіпаємо.

**Наслідки.** Найширша сумісність із TTS-екосистемою. Втрачаємо новинки 3.12+ —
для цього проєкту несуттєво.

**Відкинуто.** Python 3.13 — ламає половину кандидатів. Окрема venv на кожен
рушій — ускладнює розробку без виграшу.

> **Обмежено пізніше (ADR-012).** Другий пункт виявився хибним у своїй підставі.
> «Без виграшу» було правдою, доки передбачалося, що всі рушії вміщаються в одне
> середовище. Перевірка показала, що `ukrainian-tts` і `chatterbox-tts` **не
> вміщаються** — конфліктів два (numpy і torch/torchaudio), і другого досить
> самого по собі. Тож окреме середовище на рушій — єдиний спосіб мати обидва, і
> це вже не ускладнення, а необхідність. Вибір **Python 3.11** цим не
> скасовується: він ухвалений з інших підстав і лишається чинним.

## ADR-003. MVP-рушії: Piper і `ukrainian-tts` (не XTTS)

**Статус:** прийнято

**Контекст.** Цільова мова — українська. Перевірено:
- **Piper** має 5 українських голосів: `uk_UA-tetiana-high`,
  `uk_UA-mykyta-high`, `uk_UA-oleksa-high` (по ~114 MB), `uk_UA-lada-x_low`
  (20 MB), `uk_UA-ukrainian_tts-medium` (77 MB, 3 спікери). Швидко на CPU.
- **`ukrainian-tts`** (robinhad, MIT, ESPNET FastPitch+HiFiGAN) — ті самі
  5 голосів, працює офлайн на CPU і навіть на ARM, має **автоматичний наголос**
  (словник + трансформерна модель). Для української це критично: неправильний
  наголос руйнує якість більше, ніж будь-яка «неемоційність».
- **XTTS-v2 підтримує 17 мов — української серед них немає.** Пошук по
  HuggingFace не знайшов жодного робочого українського файнтюну XTTS:
  єдиний кандидат `mouseyy/xttsv2-ukrainian_220123` містить лише `config.json`,
  без ваг.

**Рішення.** MVP підтримує два українські рушії за спільним інтерфейсом:
Piper (як рушій за замовчуванням, через OpenAI-сумісний сервер) і
`ukrainian-tts` (як рушій із найкращим наголосом, прямий in-process адаптер).
XTTS-v2 у MVP не використовується.

**Наслідки.** Застосунок працює на цій машині без GPU вже на етапі 1.
Виразність на MVP забезпечує шар виразу (ADR-004), а не модель.

> **Уточнено пізніше (див. ADR-011).** Під час дослідження знайшовся **ZONOS2**
> — відкрита модель з українською (Tier 3), нативним виразом, клонуванням
> голосу, ліцензією Apache-2.0 і **офіційною CPU-збіркою**. Це не скасовує
> ADR-003: MVP усе одно будується на Piper, бо той працює гарантовано й швидко,
> а ZONOS2 потребує ~5 GB диска та неперевіреної швидкості на CPU. Але
> формулювання «моделі, які вміють емоції, українську не підтримують» —
> **хибне**, і в ADR-004 його виправлено.

**Відкинуто.**
- XTTS-v2 як основа — немає української; плюс ваги під Coqui Public Model
  License (некомерційна).
- `facebook/mms-tts-ukr` і `speecht5_common_voice_uk` — значно гірша якість,
  немає переваг.
- Хмарні API як основа — суперечить вимозі «відкриті моделі»; залишаються як
  опційний адаптер.

## ADR-004. Виразність як окремий шар, а не властивість моделі

**Статус:** прийнято

**Контекст.** Головна мета проєкту — «переказ тексту з виразом». Але:
- Piper і `ukrainian-tts` емоцій не вміють — вони читають рівно, і це
  **гарантовано доступні** рушії на цій машині;
- більшість моделей, які вміють емоції (Chatterbox, IndexTTS-2, Orpheus,
  Higgs Audio v2, Dia), українську **не** підтримують;
- отже, якби виразність залежала лише від моделі, на MVP ми мали б **нуль
  виразності** для української.

> **Уточнено пізніше (ADR-011).** Останній пункт більше не абсолютний: **ZONOS2**
> уміє і вираз, і клонування голосу, і підтримує українську. Але він важкий
> (~5 GB), потребує окремого нативного сервера і має **неперевірену** швидкість
> на CPU. Тому рішення не змінюється: шар виразу потрібен, бо (а) на MVP рушієм
> є Piper, (б) паузи, структура книги й гучність потрібні для будь-якого рушія,
> (в) якщо ZONOS2 виявиться повільним або неякісним українською, шар виразу —
> це те, що залишиться працювати.

**Рішення.** Виразність реалізується двома незалежними шляхами:

1. **Нативний шлях** — якщо рушій уміє емоції (теги `[laugh]`,
   `exaggeration`, emotion-вектор, інструкції природною мовою), застосунок
   передає розмітку рушію як є.
2. **Шар виразу (працює завжди)** — застосунок сам перетворює розмітку в
   керовані параметри:
   - **розмітка тексту**: розмітка рівня абзацу/речення у
     редакторі — `emotion` (neutral / warm / serious / joyful / sad / tense /
     excited) + `intensity` (0..1) + `pause_after_ms`;
   - **параметри рушія**: `speed` / `length_scale`, `noise_scale`,
     `noise_w` (Piper), `temperature` (XTTS-подібні);
   - **пост-обробка аудіо**: коригування темпу, висоти тону та енергії
     (ffmpeg `atempo`/`asetrate`/`rubberband`, або `sox`), вставка пауз,
     нормалізація гучності до цільового LUFS.

   Таблиця відповідності «емоція → параметри» живе в одному файлі
   (`app/services/expression/profiles.py`) і легко тюнінгується.

**Наслідки.**
- Виразний результат досяжний **уже на MVP** і на слабкому залізі.
- Той самий шар працює і для Chatterbox, коли той з'явиться, — просто
  «нативний шлях» перекриває частину параметрів.
- Це **не** замінює справжню акторську гру моделі. Формулюємо чесно: шар
  виразу дає керовану просодію (темп, паузи, інтонаційний контур, гучність),
  а не гру. Справжня гра — на етапі 3 через нативні моделі для тих мов, де
  вони є.
- Ризик: надмірна пост-обробка (сильний зсув тону) звучить штучно. Мітигація —
  консервативні діапазони за замовчуванням + A/B-прослуховування в UI.

**Відкинуто.** Чекати, доки з'явиться виразна українська модель — проєкт не
дасть нічого протягом невизначеного часу.

## ADR-005. `openedai-speech` замінено на **Speaches**

**Статус:** прийнято

**Контекст.** Користувач назвав `openedai-speech`. Перевірка README показала, що
проєкт **офіційно застарів**: *«This software is mostly obsolete and will no
longer be updated»*, останній реліз 0.18.2 від 2024-08-16. Автор сам радить
альтернативи: Speaches, Kokoro-FastAPI, Auralis.

**Рішення.** За OpenAI-сумісний TTS-шлюз беремо **Speaches**
(`speaches-ai/speaches`, сайт speaches.ai) — прямий ідейний наступник:
OpenAI-сумісний API, Piper + Kokoro, динамічне завантаження/вивантаження
моделей, Docker Compose, CPU і GPU, бонусом STT на `faster-whisper`.
`openedai-speech` залишається як **резервний варіант** — він усе ще працює, і
його `voice_to_speaker.yaml` / `pre_process_map.yaml` — корисний зразок
конфігурації (мапінг голосів і regex-виправлення вимови).

**Наслідки.** Застосунок спілкується з рушієм через `/v1/audio/speech`, тому
заміна шлюзу не зачіпає код. Голоси Piper реєструються так само.

**Відкинуто.** Тримати застарілий `openedai-speech` як основу — немає оновлень,
немає виправлень безпеки, прив'язка до старого `torch`.

## ADR-006. Без жорсткої залежності від ffmpeg у базовому циклі

**Статус:** прийнято

**Контекст.** На машині `ffmpeg` є **лише як snap** (v4.3.1), нативних
`/usr/bin/ffmpeg` і `/usr/bin/ffprobe` немає. Snap-версія конфайнена і
ненадійно працює з довільними шляхами до файлів — саме те, що потрібно
застосунку. Крім того, ffmpeg 4.3 застарілий.

**Рішення.**
- Базовий цикл (WAV → склеювання → нормалізація → MP3) робимо **чистим
  Python**: `soundfile` (BSD, читання/запис WAV/FLAC/OGG) + `lameenc`
  (MP3-енкодер, без зовнішніх бінарників) + `pyloudnorm` (EBU R128 / LUFS).
- `ffmpeg` стає **опційною** залежністю — потрібен лише для M4B/AAC і
  просунутої зміни темпу/тону.
- Якщо ffmpeg потрібен — ставити **нативний** через `sudo apt install ffmpeg`
  (дасть v6/v7 + `ffprobe`), а не використовувати snap. Перед цим перевірити,
  що snap-версія не заважає через `PATH`.

**Наслідки.** Менше точок відмови, простіша установка, передбачуваний звук.
Втрачаємо зручні фільтри ffmpeg там, де вони справді потрібні, — але це
ізольовано в одному модулі пост-обробки.

## ADR-007. Черга завдань: власний воркер in-process + SQLite, без Celery

**Статус:** прийнято

**Контекст.** Застосунок — локальний, для одного користувача. Синтез розділу
книги може тривати десятки хвилин, тому потрібен фоновий прогрес. Але
Celery/RQ/dramatiq тягнуть Redis або RabbitMQ — ще один сервіс у
`docker-compose` заради одного користувача.

**Рішення.** Асинхронний воркер у тому ж процесі (`asyncio.Task` + пул на
N паралельних синтезів), стан завдань у **SQLite**, прогрес у браузер — через
**SSE** (`sse-starlette`). `BackgroundTasks` FastAPI не використовуємо: він не
дає ні прогресу, ні скасування, ні відновлення після перезапуску.

**Наслідки.** Один процес, одна БД, нуль додаткових сервісів. Обмеження:
завдання не переживають падіння процесу — мітигація: кожен сегмент пишеться на
диск окремим файлом, тому після перезапуску синтез продовжується з місця
зупинки (ідемпотентність на рівні сегмента). Якщо колись знадобиться
багатокористувацький режим — інтерфейс воркера дозволяє замінити його на
Celery без зміни API.

## ADR-008. Фронтенд: Jinja2 + htmx + Alpine.js, без збірки

**Статус:** прийнято

**Контекст.** Екран MVP — це: список абзаців, кожен редагований, з вибором
голосу/емоції та кнопкою «прослухати», плюс черга завдань із прогресом.
Gradio/Streamlit дають швидкий старт, але погано підходять для щільного
редактора з контролами на кожен блок і для SSE-прогресу. React/Vite — це
окремий тулчейн, збірка і два процеси під час розробки.

**Рішення.** Серверний рендеринг: **Jinja2 + htmx** (часткові оновлення, SSE)
**+ Alpine.js** (локальний стан: відкриті панелі, редактор). Стилі — Tailwind
через CDN на час розробки, потім зібраний CSS. FastAPI віддає і HTML, і API з
одного процесу.

**Наслідки.** Нуль кроків збірки, один процес, весь стан — на сервері, що
природно для документо-центричного UI. Якщо згодом знадобиться SPA — API вже
відокремлений (`/api/v1`), тож перехід не ламає бекенд.

**Відкинуто.** Gradio — швидкий прототип, але боротьба з ним починається рівно
тоді, коли треба редактор на кожен абзац. Streamlit — та сама проблема плюс
модель перезапуску скрипта погано лягає на фонові завдання.

## ADR-009. Витяг тексту: `markitdown` як основа, `PyMuPDF` для PDF

**Статус:** прийнято

**Контекст.** Потрібні `.md`, `.pdf`, `.txt` (і бажано `.docx`, `.epub`,
`.html`). `docling` (IBM) дає найкращу якість на складних PDF, але важкий
(тягне моделі, повільний на CPU). `unstructured` — теж важкий.
`PyMuPDF` дає найшвидший і найточніший текст із «цифрових» PDF, але під
**AGPL-3.0** (для локального приватного застосунку це прийнятно; для
розповсюдження — ні).

**Рішення.** Каскад екстракторів за розширенням:
- `.txt` / `.md` — пряме читання + парсинг Markdown;
- `.pdf` — спершу `PyMuPDF` (швидко, добре на цифрових PDF); якщо тексту
  майже немає (скан) — повідомити користувача і запропонувати OCR;
- `.docx` / `.html` / `.epub` — `markitdown`;
- OCR для сканів — окремий опційний модуль (Tesseract або `surya`), не в MVP.

Усі екстрактори повертають **однакову проміжну модель** — список блоків
(`heading` / `paragraph` / `quote` / `list_item` / `table`) зі збереженням
порядку. Далі працюємо тільки з нею.

**Наслідки.** Швидко, без важких залежностей, із запасним шляхом. AGPL-ризик
зафіксовано явно.

## ADR-010. Шлях «український XTTS» визнано недоступним

**Статус:** прийнято (фіксація неможливості)

**Контекст.** Найспокусливіший сценарій — XTTS-v2 із клонуванням голосу по
3-секундному семплу + український файнтюн. Перевірено: XTTS-v2 підтримує
17 мов, української немає; пошук по HuggingFace (`ukrainian tts`,
`xtts ukrainian`, `uk tts`) не знайшов жодного чекпойнта XTTS з українськими
вагами.

**Рішення.** Не планувати робіт навколо **саме цього** шляху.

**Наслідки.** Клонування голосу для української через XTTS неможливе.

> **Обмежено пізніше (ADR-011).** Цей ADR стосується **виключно XTTS-v2**.
> Початкове формулювання наслідків було ширшим — «клонування голосу для
> української не буде взагалі» — і **виявилося хибним**: ZONOS2 уміє
> клонування голосу й підтримує українську. Не видаляю первісний висновок, щоб
> було видно, де перевірка була неповною.

## ADR-011. ZONOS2 — кандидат на «вираз + українська», але не в MVP

**Статус:** прийнято

**Контекст.** Під час дослідження знайшлася модель, яка ламає головне
обмеження проєкту — **ZONOS2** (Zyphra). Перевірено з картки моделі та
README `zonos2.cpp`:

- **~7.6B MoE**, навчено на 6+ млн годинах багатомовного мовлення;
- **українська підтримується** (Tier 3; Tier 1 — англійська, китайська,
  японська; Tier 2 — 10 мов, серед них російська);
- заявлено вираз і якість «на рівні або вище провідних TTS-провайдерів»;
- **клонування голосу** — «high-fidelity and naturalistic», in-process;
- **ліцензія Apache-2.0** — і ваги, і GGUF;
- `zonos2.cpp` — нативний C++/ggml порт: увесь конвеєр виконується без Python,
  PyTorch і CUDA-ядер, працює на **CPU**, CUDA, Metal і Vulkan;
- дає `zonos2-server` з **OpenAI-сумісним `/v1/audio/speech`** і потоковим PCM;
- кванти від `q4_k` (4.92 GB) до `f16` (15.34 GB); Q4_K заявлено як такий, що
  звучить «within eval noise of F16».

Це єдина знайдена відкрита модель, яка одночасно дає вираз, українську,
клонування голосу й дозвільну ліцензію.

**Рішення.** ZONOS2 стає **основним кандидатом етапу 3**, а не частиною MVP.
Умова входу — три перевірки, які ще не зроблено:

1. **якість української** — прослуховування (Tier 3 — це класифікація
   покриття, а не оцінка якості; вимірювань для української не знайдено);
2. **швидкість на CPU** — README обіцяє реальний час лише **на GPU**;
3. **диск** — `q4_k` + допоміжні файли ≈ 5.2 GB проти 11 GB вільного.

**Наслідки.**
- Архітектура не змінюється: ZONOS2 підключається як третій адаптер за
  інтерфейсом `TTSEngine` (ADR-001) через `openai_compat`, бо має OpenAI-сумісний
  ендпоінт. Це рівно той випадок, заради якого абстракція закладалася.
- Шар виразу (ADR-004) залишається: паузи, структура книги й LUFS потрібні
  для будь-якого рушія, а Piper залишається швидким режимом для перегляду.
- Python 3.11 (ADR-002) для ZONOS2 не потрібен — це нативний бінарник.
- `ffmpeg` ZONOS2 потребує **лише** для клонування голосу (декодування
  референсу); звичайний синтез без нього працює. Це узгоджується з ADR-006.

**Ризик, який приймаємо.** Якщо українська в ZONOS2 звучить погано або CPU
виявиться надто повільним — викреслюємо його, і план MVP не змінюється взагалі.
ZONOS2 — **підвищення якості, а не передумова**. Саме тому він в етапі 3.

**Відкинуто.**
- Будувати MVP одразу на ZONOS2 — блокує проєкт на невиміряних припущеннях і
  вимагає ~5 GB диска, якого зараз немає.
- Ігнорувати ZONOS2 — втратити єдиний відомий шлях до справжнього виразу
  українською на відкритій моделі.

## ADR-012. `uk` і `expressive` не вміщаються в одне середовище

**Статус:** прийнято

**Контекст.** Спроба поставити обидва необов'язкові набори разом завершується
помилкою резолвера:

```
Because all versions of ukrainian-tts depend on numpy>=2.3.0
and chatterbox-tts==0.1.7 depends on numpy>=1.24.0,<2.0.0,
we can conclude that chatterbox-tts==0.1.7 and all versions of
ukrainian-tts are incompatible.
```

Перевірено (uv 0.9.17, CPython 3.11.16, `chatterbox-tts` 0.1.7 — найновіша,
`ukrainian-tts` 6.0.2 — найновіша): це **не один** конфлікт про numpy, а **два
незалежні**.

1. **numpy.** `chatterbox-tts` на Python < 3.13 вимагає `numpy>=1.24,<2.0.0`;
   `ukrainian-tts` — `numpy>=2.3.0`.
2. **torch / torchaudio.** `chatterbox-tts` тримає рівно `torch==2.6.0` і
   `torchaudio==2.6.0` (для Python < 3.14); `ukrainian-tts` напряму вимагає
   `torch>=2.8.0` і `torchaudio>=2.8.0` (і додатково тримає `espnet==202509`).

Другий конфлікт видно, лише якщо **примусово** зняти перший: з
`--override numpy>=2.3.0` резолвер одразу впирається в
`torchaudio==2.6.0` проти `>=2.8.0`. Це головний висновок: **«послабити numpy»
проблему не вирішує**. Конфлікт не в дрібниці піна, а в розбіжності поколінь
torch-ABI — бібліотеки, на якій стоять обидва рушії.

Кожен набір окремо резолвиться бездоганно: `uk` → numpy 2.4.6 + torch 2.12.1,
`expressive` → numpy 1.26.4 + torch 2.6.0.

**Рішення.**

1. Оголосити набори взаємно несумісними в `pyproject.toml`
   (`[tool.uv] conflicts`). `uv lock` резолвить обидва в **окремих гілках**,
   тож лок-файл існує й CI не падає, а спроба поставити їх в один інтерпретатор
   дає явну помилку з назвою конфлікту замість ребуса про numpy.
2. Рушій, чий стек конфліктує з поточним середовищем, підключається **через
   межу процесу** — через `openai_compat` (ADR-001), а не імпортом у той самий
   процес. Одне середовище містить рівно **один** torch-стек.
3. `services/tts/chatterbox.py` (етап 3.2) лишається in-process адаптером лише
   в середовищі **без** `uk`. Якщо колись знадобляться обидва одночасно —
   Chatterbox виноситься в окремий процес за тим самим інтерфейсом.

**Наслідки.**
- `uv lock` більше не падає, а помилка стала дієвою: вона називає конфлікт і
  підказує, що робити.
- З'являється вимога до застосунку: `GET /api/v1/engines` не може просто
  перелічувати рушії — частина з них недоступна в поточному середовищі.
  `capabilities()` (ADR-001) має повідомляти про недоступність **явно**, а
  адаптер — не падати на імпорті важкої залежності.
- Диск: два стеки — це два `torch` (разом ~5–14 GB) при **11 GB вільного**
  (ENVIRONMENT.md). Навіть якби ABI збігався, місця під обидва зараз немає,
  тож на практиці це обмеження поки нічого не коштує.

**Відкинуто.**
- **Примусово зняти піни** (`numpy>=2.3` + torch 2.8 для Chatterbox). Chatterbox
  зібраний і протестований проти `torch==2.6.0` і додатково тримає
  `transformers==5.2.0`, `diffusers==0.29.0`. Отримали б середовище, яке
  **резолвиться, але ламається в рантаймі** — гірше за чесну помилку: помилка
  резолвера коштує хвилини, а зламаний інференс — годин.
- **Перейти на Python 3.13**, бо там Chatterbox вимагає `numpy>=2.0.0` і
  конфлікт про numpy зникає. Не рятує: `torch==2.6.0` у нього закріплено для
  `python_version < 3.14`, тож конфлікт із `torch>=2.8.0` лишається; плюс
  ADR-002 і колеса `espnet`.
- **Лишити один рушій, другий викинути.** Українська й англійська — різні
  задачі, і PLAN 3.2 тримає обидва навмисно (ADR-004).
- **Окрема venv на кожен рушій** — саме це ADR-002 відкинув як «ускладнення без
  виграшу». Підстава того висновку виявилася хибною; див. уточнення в ADR-002.
